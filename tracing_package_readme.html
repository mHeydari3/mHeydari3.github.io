1. نمای کلی پکیج (Overview)

tracingpackage یک لایه انتزاعی (abstraction layer) جامع و با طراحی خوب بر روی OpenTelemetry Go SDK برای فعال‌سازی و مدیریت Distributed Tracing در برنامه‌های کاربردی Go است. هدف اصلی این پکیج، ساده‌سازی فرآیند پیچیده راه‌اندازی، پیکربندی و استفاده از OpenTelemetry است، در حالی که بهترین شیوه‌ها (best practices) مانند تزریق وابستگی (Dependency Injection) و قابلیت تست (testability) را ترویج می‌دهد.

این پکیج به توسعه‌دهندگان اجازه می‌دهد تا بدون درگیر شدن با جزئیات سطح پایین OTel SDK، به راحتی tracing را به برنامه‌های خود اضافه کنند. این کار از طریق ارائه:

  • پیکربندی یکپارچه: بارگذاری تنظیمات از فایل (YAML) و متغیرهای محیطی با استفاده از Viper.
  • راه‌اندازی خودکار اجزای OTel: ایجاد و پیکربندی خودکار TracerProvider, Resource, Sampler, SpanExporter, و Propagator.
  • اینترفیس‌های ساده: ارائه اینترفیس‌های Tracer و Span که APIهای اصلی OTel را wrap می‌کنند و استفاده از آن‌ها را آسان‌تر می‌سازند.
  • توابع کمکی Context: توابع کاربردی برای تعامل آسان با Span فعال در context.Context.
  • جداسازی دغدغه‌ها: تفکیک منطق مربوط به sampling و propagation در زیر-پکیج‌های مجزا.
  • تمرکز بر تزریق وابستگی: طراحی شده برای استفاده آسان در کنار الگوهای تزریق وابستگی، به جای تکیه بر نمونه‌های سراسری (globals) OTel.

در نهایت، tracingpackage به عنوان یک “جعبه ابزار” عمل می‌کند که تمام قطعات لازم برای پیاده‌سازی tracing به روشی استاندارد، قابل نگهداری و قابل تست را در اختیار توسعه‌دهندگان قرار می‌دهد.

2. چرا این پکیج ساخته شده؟ (Motivation & Benefits)

پیاده‌سازی Distributed Tracing با استفاده مستقیم از OpenTelemetry Go SDK قدرتمند است، اما می‌تواند شامل پیچیدگی‌ها و کدهای تکراری (boilerplate) قابل توجهی باشد، به خصوص در برنامه‌های بزرگ یا میکروسرویس‌ها. tracingpackage برای رفع این نگرانی‌ها و ارائه مزایای زیر ساخته شده است:

  • ساده‌سازی راه‌اندازی (Simplified Setup): OTel نیازمند پیکربندی چندین جزء کلیدی است: Resource, Exporter, Sampler, SpanProcessor, TracerProvider, Propagator. انجام صحیح این کار می‌تواند زمان‌بر و مستعد خطا باشد. tracingpackage این فرآیند را در تابع NewTracerProvider کپسوله می‌کند و تنها با یک Config ورودی، تمام این اجزا را به درستی تنظیم می‌نماید.
  • پیکربندی متمرکز و انعطاف‌پذیر (Centralized & Flexible Configuration): مدیریت تنظیمات tracing (مانند فعال/غیرفعال بودن، نام سرویس، نوع اکسپورتر، آدرس‌ها، نرخ نمونه‌برداری، فرمت‌های انتشار) در یک مکان واحد (فایل YAML و/یا متغیرهای محیطی) بسیار کارآمدتر از پخش کردن این تنظیمات در کد است. استفاده از Viper انعطاف‌پذیری بالایی را فراهم می‌کند.
  • ترویج تزریق وابستگی (Dependency Injection Promotion): OpenTelemetry از ثبت سراسری (global registration) برای TracerProvider و Propagator پشتیبانی می‌کند. در حالی که این کار برای شروع سریع مفید است، در برنامه‌های بزرگ منجر به وابستگی‌های پنهان و دشواری در تست می‌شود. tracingpackage با برگرداندن TracerProvider و Propagator (به جای ثبت سراسری آن‌ها)، توسعه‌دهندگان را تشویق می‌کند تا این وابستگی‌ها را به صراحت به کامپوننت‌هایی که به آن‌ها نیاز دارند (مانند Middleware, Handlers, Services) تزریق کنند. این امر منجر به کدی ماژولارتر، قابل نگهداری‌تر و به شدت قابل تست‌تر می‌شود.
  • انتزاع و جداسازی (Abstraction & Decoupling): با ارائه اینترفیس‌های Tracer و Span، کد برنامه از جزئیات پیاده‌سازی داخلی OTel SDK جدا می‌شود. این بدان معناست که:
    • کد برنامه ساده‌تر و خواناتر می‌شود زیرا با API سطح بالاتری کار می‌کند.
    • اگر در آینده نیاز به تغییر کتابخانه tracing (هرچند بعید با وجود استاندارد OTel) یا تغییرات عمده در OTel SDK باشد، بیشترین تأثیر در داخل tracingpackage محدود می‌شود و کد اصلی برنامه کمتر تحت تأثیر قرار می‌گیرد.
    • تست‌پذیری (Testability): این مهم‌ترین مزیت انتزاع است. در تست‌های واحد (unit tests)، می‌توان به راحتی پیاده‌سازی‌های mock یا fake از اینترفیس‌های Tracer و Span را به کد تزریق کرد و رفتار tracing را بدون نیاز به راه‌اندازی کل پشته OTel یا ارسال spanهای واقعی، شبیه‌سازی و تأیید کرد.
  • کاهش کد تکراری (Reduced Boilerplate): وظایف رایج مانند ایجاد Span، افزودن Attribute، ثبت Event یا خطا، و پایان دادن به Span از طریق اینترفیس‌ها و توابع کمکی Context ساده‌سازی شده‌اند. Middleware و instrumentationهای خودکار (که می‌توانند با این پکیج استفاده شوند) نیز به شدت کد دستی مورد نیاز را کاهش می‌دهند.
  • سازگاری و استانداردسازی (Consistency & Standardization): با فراهم کردن یک راه واحد و توصیه شده برای راه‌اندازی و استفاده از tracing در کل سازمان یا پروژه، این پکیج به حفظ سازگاری در نحوه تولید تله‌متری کمک می‌کند.

اگر نخواهیم از این Package استفاده کنیم چه منفعتی را از دست می‌دهیم؟

عدم استفاده از tracingpackage به معنای تعامل مستقیم با OpenTelemetry Go SDK است. در این صورت:

  1. پیچیدگی بیشتر در راه‌اندازی: شما مسئولیت کامل پیکربندی دستی تمام اجزای OTel (Provider, Exporter, Sampler, Resource, Processor, Propagator) را در هر سرویس یا برنامه خواهید داشت.
  2. کد تکراری بیشتر: کد مربوط به راه‌اندازی OTel احتمالاً در چندین سرویس تکرار خواهد شد.
  3. وابستگی مستقیم به OTel SDK: کد شما مستقیماً به انواع و APIهای OTel وابسته خواهد بود که می‌تواند تست واحد را دشوارتر کند (نیاز به استفاده از ابزارهای تست OTel یا NoOp providerها) و تغییرات احتمالی در آینده را سخت‌تر نماید.
  4. عدم وجود API ساده‌سازی شده: شما از اینترفیس‌های Tracer و Span و توابع کمکی Context این پکیج بی‌بهره خواهید بود و باید مستقیماً با oteltrace.Tracer و oteltrace.Span کار کنید.
  5. مدیریت پیکربندی پراکنده: احتمالاً مجبور خواهید بود راهکار خود را برای مدیریت پیکربندی tracing در سرویس‌های مختلف پیاده‌سازی کنید.

به طور خلاصه، tracingpackage یک سرمایه‌گذاری اولیه کوچک در جهت سادگی، قابلیت نگهداری و تست‌پذیری بلندمدت است، به خصوص در محیط‌های میکروسرویسی.

3. مفاهیم کلیدی OpenTelemetry (Key Concepts)

برای درک کامل tracingpackage و Distributed Tracing به طور کلی، آشنایی با مفاهیم اصلی OpenTelemetry ضروری است. این پکیج این مفاهیم را کپسوله و ساده می‌کند، اما دانستن آن‌ها به فهم عمیق‌تر کمک می‌کند:

  • Trace: یک Trace کل مسیر یک درخواست را هنگام عبور از بخش‌های مختلف یک سیستم توزیع‌شده (میکروسرویس‌ها، دیتابیس‌ها، صف‌های پیام و …) نشان می‌دهد. یک Trace مجموعه‌ای از Spanهای مرتبط به هم است که همگی یک Trace ID منحصر به فرد دارند.
  • Span: واحد اصلی کار در یک Trace است. هر Span یک عملیات یا دوره زمانی مشخص را نشان می‌دهد (مثلاً پردازش یک درخواست HTTP، یک کوئری دیتابیس، اجرای یک تابع). Spanها دارای ویژگی‌های زیر هستند:
    • Operation Name: نامی که عملیات را توصیف می‌کند (مثلاً HTTP GET /users, db.query, UserService.GetUser).
    • Start & End Timestamps: زمان شروع و پایان عملیات، که مدت زمان (Duration) آن را مشخص می‌کند.
    • Span Context: مجموعه‌ای از شناسه‌ها که Span را در Trace قرار می‌دهند و امکان انتشار آن را فراهم می‌کنند:
      • Trace ID: شناسه یکتای کل Trace.
      • Span ID: شناسه یکتای خود Span.
      • Parent Span ID (اختیاری): Span ID والدی که این Span را ایجاد کرده است (برای ایجاد ساختار درختی).
      • Trace Flags: اطلاعات اضافی مانند اینکه آیا Trace نمونه‌برداری (sampled) شده است.
      • Trace State: اطلاعات اضافی vendor-specific.
    • Attributes (یا Tags): جفت‌های کلید-مقدار که متادیتای عملیات را توصیف می‌کنند (مثلاً http.method="GET", db.system="postgresql"). OpenTelemetry Semantic Conventions نام‌های استانداردی برای این کلیدها تعریف می‌کند.
    • Events (یا Logs): رکوردهای زمانی از رویدادهای خاص در طول عمر Span (مثلاً یک خطا، یک پیام خاص).
    • Status: وضعیت پایان عملیات (OK, Error, Unset).
    • Kind: نوع Span که نقش آن را مشخص می‌کند (SERVER, CLIENT, PRODUCER, CONSUMER, INTERNAL).
  • TracerProvider: کارخانه‌ای برای ایجاد Tracerها. این آبجکت تنظیمات کلی Tracing را نگه می‌دارد:
    • Resource: مجموعه‌ای از Attributes که سرویس یا نمونه‌ای که تله‌متری را تولید می‌کند، توصیف می‌کند (مثلاً service.name, service.version).
    • Sampler: منطقی که تصمیم می‌گیرد کدام Traceها باید به طور کامل ثبت و ارسال شوند.
    • SpanProcessor: مسئول پردازش Spanها (مانند دسته‌بندی - Batching) قبل از ارسال به Exporter. BatchSpanProcessor رایج‌ترین است.
    • SpanExporter: مسئول ارسال Spanهای پردازش شده به یک سیستم Backend (مانند Jaeger, Zipkin, OTLP Collector, Console).
  • Tracer: آبجکتی که از TracerProvider دریافت می‌شود و برای شروع (Start) کردن Spanهای جدید استفاده می‌شود. هر Tracer معمولاً با نام کتابخانه یا کامپوننتی که از آن استفاده می‌کند، مشخص می‌شود.
  • Propagator: مکانیزمی برای سریال‌سازی (Inject) Span Context در یک حامل (Carrier) مانند هدرهای HTTP و دی‌سریال‌سازی (Extract) آن در سمت دیگر. این امر امکان پیوند دادن Spanها در مرزهای شبکه یا فرآیند را فراهم می‌کند. استانداردهای رایج عبارتند از:
    • W3C Trace Context: استاندارد وب توصیه شده (هدرهای traceparent و tracestate).
    • B3: فرمت رایج دیگر (هدرهای X-B3-* یا یک هدر b3).
  • Context (در Go: context.Context): مکانیزم استاندارد Go برای حمل داده‌های مربوط به یک درخواست، مهلت‌ها و سیگنال‌های لغو در طول زنجیره فراخوانی‌ها. OpenTelemetry از context.Context برای حمل Span Context فعال استفاده می‌کند. پاس دادن صحیح ctx بین توابع و goroutineها برای حفظ زنجیره Trace حیاتی است.
  • Semantic Conventions: مجموعه‌ای از نام‌ها و مقادیر استاندارد برای Attributeها، نام Spanها و Eventها که توسط OpenTelemetry تعریف شده‌اند. استفاده از آن‌ها باعث می‌شود تله‌متری تولید شده در ابزارهای مختلف Observability به طور یکسان قابل فهم و تحلیل باشد (مثلاً کلیدهای http.method, db.statement, rpc.system).

tracingpackage بسیاری از این مفاهیم را در پشت اینترفیس‌ها و توابع خود پنهان می‌کند، اما دانستن آن‌ها به شما کمک می‌کند تا بفهمید در پشت صحنه چه اتفاقی می‌افتد و چگونه پیکربندی‌ها بر رفتار tracing تأثیر می‌گذارند.

4. ساختار پکیج (Package Structure)

tracingpackage/
    ├── config.go               # تعریف ساختارهای Config، بارگذاری با Viper، اعتبارسنجی
    ├── doc.go                  # مستندات پکیج (godoc)
    ├── errors.go               # تعریف خطاهای استاندارد پکیج
    ├── provider.go             # منطق اصلی ایجاد OTel TracerProvider، Exporter، Resource
    ├── span.go                 # تعریف اینترفیس Span و پیاده‌سازی wrapper آن
    ├── tracer.go               # تعریف اینترفیس Tracer، پیاده‌سازی wrapper و توابع کمکی Context
    │
    ├── propagation/            # زیر-پکیج مربوط به انتشار Context
    │   ├── carriers.go         # پیاده‌سازی TextMapCarrier برای HTTP و gRPC
    │   └── propagator.go       # ایجاد OTel Propagator (معمولاً Composite) و توابع Inject/Extract
    │
    └── sampling/               # زیر-پکیج مربوط به نمونه‌برداری
        └── sampler.go          # ایجاد OTel Sampler بر اساس پیکربندی
  • ریشه پکیج (tracingpackage/): شامل فایل‌های اصلی برای پیکربندی (config.go)، راه‌اندازی Provider (provider.go)، اینترفیس‌ها و wrapperهای اصلی (tracer.go, span.go)، خطاها (errors.go) و مستندات (doc.go).
  • propagation/: تمام کدهای مربوط به نحوه انتقال Span Context بین سرویس‌ها در این زیر-پکیج قرار دارد. این شامل تعریف Carrierها (چگونه داده‌ها حمل می‌شوند) و منطق ساخت Propagator (کدام فرمت‌ها پشتیبانی می‌شوند) است.
  • sampling/: کد مربوط به تصمیم‌گیری در مورد اینکه کدام Traceها باید ثبت شوند، در این زیر-پکیج قرار دارد و یک Sampler مناسب بر اساس پیکربندی ایجاد می‌کند.

این ساختار به تفکیک بهتر دغدغه‌ها (Separation of Concerns) کمک می‌کند و نگهداری و توسعه پکیج را آسان‌تر می‌نماید.

5. پیکربندی (Configuration)

پیکربندی tracingpackage از طریق فایل config.go مدیریت می‌شود و از کتابخانه Viper برای انعطاف‌پذیری بالا استفاده می‌کند. تنظیمات می‌توانند از منابع زیر بارگذاری شوند (با اولویت بالاتر برای منابع پایین‌تر لیست):

  1. مقادیر پیش‌فرض (Defaults): مقادیر از پیش تعریف شده در کد (default* constants).
  2. فایل پیکربندی (Config File): یک فایل YAML (یا فرمت‌های دیگر پشتیبانی شده توسط Viper) که در مسیرهای مشخصی جستجو می‌شود (مثلاً ./tracing.yaml, ./config/tracing.yaml).
  3. متغیرهای محیطی (Environment Variables): با پیشوند TRACING_ و جایگزینی . با _ (مثلاً TRACING_EXPORTER_TYPE, TRACING_SAMPLER_RATIO).

ساختار پیکربندی (Config struct):

  • Enabled (bool): فعال یا غیرفعال کردن کامل tracing. اگر false باشد، یک NoOp provider برگردانده می‌شود و هیچ spanی تولید یا ارسال نخواهد شد. (پیش‌فرض: true)
  • ServiceName (string): (ضروری) نام سرویس شما که در تله‌متری ثبت می‌شود (مثلاً user-service, order-api). این برای شناسایی منبع spanها حیاتی است. (پیش‌فرض: unknown-service - باید حتما override شود)
  • ServiceVersion (string): نسخه سرویس شما (مثلاً 1.2.0). (پیش‌فرض: 0.0.0)
  • Environment (string): محیط استقرار (مثلاً production, staging, development). (پیش‌فرض: development)
  • Exporter: تنظیمات مربوط به نحوه ارسال spanها به Backend.
    • Type (string): نوع اکسپورتر (jaeger, otlp_grpc, otlp_http, console, none). (پیش‌فرض: none)
    • Jaeger: تنظیمات خاص Jaeger.
      • Endpoint (string): آدرس Jaeger Collector (مثلاً http://localhost:14268/api/traces).
      • Username, Password (string, optional): برای Basic Auth.
    • OTLP: تنظیمات خاص OTLP (برای gRPC و HTTP).
      • Endpoint (string): آدرس OTLP Collector (مثلاً localhost:4317 برای gRPC, localhost:4318 برای HTTP).
      • Insecure (bool): استفاده از TLS یا خیر. (پیش‌فرض: true برای توسعه آسان‌تر)
      • Headers (map[string]string): هدرهای اضافی برای ارسال (مثلاً برای احراز هویت).
      • Timeout (time.Duration): مهلت زمانی برای ارسال spanها.
  • Sampler: تنظیمات مربوط به نمونه‌برداری traceها.
    • Type (string): نوع سمپلر (always_on, always_off, trace_id_ratio). (پیش‌فرض: always_on)
    • Ratio (float64): نرخ نمونه‌برداری بین 0.0 تا 1.0 (فقط برای trace_id_ratio). (پیش‌فرض: 1.0)
  • Propagation: تنظیمات مربوط به فرمت‌های انتشار Context.
    • Formats (string): لیست فرمت‌های جدا شده با کاما (tracecontext, baggage, b3, b3multi). (پیش‌فرض: tracecontext,baggage)

مثال فایل tracing.yaml:

# فعال کردن tracing
    enabled: true
    
    # اطلاعات سرویس (بسیار مهم - حتما تنظیم کنید)
    service_name: "product-api"
    service_version: "v1.5.2"
    environment: "production"
    
    # تنظیمات اکسپورتر: ارسال به OTLP Collector از طریق gRPC
    exporter:
      type: "otlp_grpc" # یا "otlp_http", "jaeger", "console", "none"
      otlp:
        endpoint: "otel-collector.observability.svc.cluster.local:4317" # آدرس کالکتور در کلاستر
        insecure: false # استفاده از TLS در پروداکشن
        timeout: 5s
        # headers: # مثال برای هدر احراز هویت

      # jaeger: # تنظیمات Jaeger اگر type="jaeger" بود
        # endpoint: "http://jaeger-collector.observability.svc.cluster.local:14268/api/traces"
    
    # تنظیمات سمپلر: نمونه‌برداری 20% از trace ها
    sampler:
      type: "trace_id_ratio" # یا "always_on", "always_off"
      ratio: 0.2

6. راهنمای استفاده (Usage Guide & Best Practices)

این بخش نحوه استفاده از tracingpackage را به شیوه‌ای که بهترین شیوه‌های صنعت نرم‌افزار (مانند تزریق وابستگی) را رعایت می‌کند، شرح می‌دهد.

مرحله 1: مقداردهی اولیه در main.go

package main
    
    import (
        "context"
        "errors"
        "log/slog"
        "net/http"
        "os"
        "os/signal"
        "syscall"
        "time"
    
        "sample-app/tracingpackage"
        tpropagation "sample-app/tracingpackage/propagation" // Alias propagation if needed
    
        "sample-app/internal/server"  // Your server package
        "sample-app/internal/service" // Your service package
    )
    
    const (
        tracingConfigName = "tracing"     // Name of the config file (tracing.yaml)
        shutdownTimeout   = 15 * time.Second
        serverAddr        = ":8080"
    )
    
    func main() {
        // 1. Setup Logger
        logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelDebug}))
        slog.SetDefault(logger) // Optional: set as global default logger
    
        // 2. Load Tracing Configuration
        tracingCfg, err := tracingpackage.LoadConfig(tracingConfigName, logger)
        if err != nil {
            logger.Error("Failed to load tracing config", "error", err)
            os.Exit(1)
        }
    
        // 3. Initialize Tracer Provider (using tracingpackage)
        //    IMPORTANT: Do NOT register globally here. Get the provider and shutdown function.
        tp, tracerShutdown, err := tracingpackage.NewTracerProvider(tracingCfg, logger)
        if err != nil {
            logger.Error("Failed to create tracer provider", "error", err)
            os.Exit(1)
        }
        // CRITICAL: Defer the shutdown function to be called before the application exits.
        defer func() {
            logger.Info("Executing TracerProvider shutdown...")
            // Use a timeout slightly less than the overall shutdown timeout.
            shutdownCtx, cancel := context.WithTimeout(context.Background(), shutdownTimeout - (2 * time.Second))
            defer cancel()
            if err := tracerShutdown(shutdownCtx); err != nil {
                logger.Error("Error shutting down tracer provider", "error", err)
            } else {
                logger.Info("TracerProvider shutdown successful.")
            }
        }()
    
        // 4. Initialize Propagator (using tracingpackage/propagation)
        propagator := tpropagation.NewPropagator(tracingCfg.Propagation.Formats)
    
        // 5. Create the main Tracer instance (using tracingpackage)
        //    Get the tracer from the provider created in step 3.
        //    Use the service name from config for the instrumentation name.
        appTracer := tracingpackage.NewTracer(tp, tracingCfg.ServiceName) // This returns the tracingpackage.Tracer interface
    
        logger.Info("Tracing initialized successfully", "config", tracingCfg) // Log config summary
    
        // --- Dependency Injection ---
    
        // 6. Create Services, injecting logger and the `tracingpackage.Tracer` interface
        workSvc := service.NewWorkService(logger, appTracer) // Assume NewWorkService accepts tracingpackage.Tracer
    
        // 7. Create Handlers/Controllers, injecting dependencies
        appHandlers := server.NewAppHandlers(logger, appTracer, workSvc) // Assume NewAppHandlers accepts tracingpackage.Tracer
    
        // --- Setup HTTP Server ---
    
        // 8. Create Router and register handlers
        mux := http.NewServeMux()
        mux.HandleFunc("GET /hello", appHandlers.HandleHello)
        mux.HandleFunc("GET /work", appHandlers.HandleWork)
    
        // 9. Create and apply Tracing Middleware
        //    Inject the logger, tracer (interface), and the OTel propagator.
        tracingMW := server.TracingMiddleware(logger, appTracer, propagator) // Assume TracingMiddleware is defined in server package
        handlerWithMiddleware := tracingMW(mux)
    
        // 10. Define and configure the HTTP server
        httpServer := &http.Server{
            Addr:    serverAddr,
            Handler: handlerWithMiddleware,
            // Add other configurations like timeouts
        }
    
        // 11. Start the server in a separate goroutine
        go func() {
            logger.Info("Starting HTTP server", "address", serverAddr)
            if err := httpServer.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
                logger.Error("HTTP server ListenAndServe error", "error", err)
                // Handle server startup failure, maybe exit or notify
                os.Exit(1)
            }
        }()
    
        // --- Graceful Shutdown ---
    
        // 12. Wait for termination signals
        stopChan := make(chan os.Signal, 1)
        signal.Notify(stopChan, syscall.SIGINT, syscall.SIGTERM)
        sig := <-stopChan
        logger.Info("Received shutdown signal", "signal", sig)
    
        // 13. Start graceful shutdown process
        logger.Info("Initiating graceful shutdown", "timeout", shutdownTimeout)
        shutdownCtx, cancelShutdown := context.WithTimeout(context.Background(), shutdownTimeout)
        defer cancelShutdown()
    
        // 14. Shutdown the HTTP server gracefully
        if err := httpServer.Shutdown(shutdownCtx); err != nil {
            logger.Error("HTTP server shutdown error", "error", err)
        } else {
            logger.Info("HTTP server shutdown complete.")
        }
    
        // The deferred tracerShutdown() will run here.
        logger.Info("Application terminated gracefully.")
    }

مرحله 2: پیاده‌سازی TracingMiddleware (مثال در internal/server/middleware.go)

این Middleware مسئولیت اصلی مدیریت Spanهای ورودی را دارد.

package server
    
    import (
        "log/slog"
        "net/http"
        "time"
    
        "sample-app/tracingpackage" // Our package
        tpropagation "sample-app/tracingpackage/propagation"
    
        "go.opentelemetry.io/otel/codes"
        "go.opentelemetry.io/otel/propagation" // OTel propagator interface
        semconv "go.opentelemetry.io/otel/semconv/v1.21.0" // Use consistent version
        oteltrace "go.opentelemetry.io/otel/trace"
    )
    
    // TracingMiddleware creates an HTTP middleware.
    // It accepts the tracingpackage.Tracer interface and the otel propagation.TextMapPropagator.
    func TracingMiddleware(logger *slog.Logger, tracer tracingpackage.Tracer, propagator propagation.TextMapPropagator) func(http.Handler) http.Handler {
        return func(next http.Handler) http.Handler {
            return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
                startTime := time.Now()
    
                // 1. Extract context from incoming headers
                carrier := tpropagation.NewHTTPHeaderCarrier(r.Header)
                requestCtx := tpropagation.Extract(r.Context(), propagator, carrier) // Use helper
    
                // 2. Start the server span using the injected Tracer interface
                spanName := r.Method + " " + r.URL.Path // Example span name
                ctx, span := tracer.Start(requestCtx, spanName, oteltrace.WithSpanKind(oteltrace.SpanKindServer))
                defer span.End(nil) // Defer End immediately, status/error set later
    
                // 3. Inject the context with the new span back into the request
                r = r.WithContext(ctx)
    
                // 4. Wrap response writer to capture status code
                rw := &responseWriter{ResponseWriter: w, statusCode: http.StatusOK}
    
                // 5. Call the next handler
                next.ServeHTTP(rw, r)
    
                // 6. Record standard HTTP attributes after handler returns
                span.SetAttributes(
                    semconv.HTTPRequestMethodKey.String(r.Method),
                    semconv.URLPathKey.String(r.URL.Path),
                    semconv.HTTPResponseStatusCodeKey.Int(rw.statusCode),
                    // Add more semantic attributes as needed...
                    semconv.ClientAddressKey.String(r.RemoteAddr),
                    semconv.UserAgentOriginalKey.String(r.UserAgent()),
                )
    
                // 7. Set span status based on HTTP status code
                if rw.statusCode >= 500 {
                    span.SetStatus(codes.Error, http.StatusText(rw.statusCode))
                } else {
                    span.SetStatus(codes.Ok, "") // Treat < 500 as OK for span status
                }
    
                // Optional: Log request summary with trace IDs
                duration := time.Since(startTime)
                logAttrs := []slog.Attr{
                    slog.String("method", r.Method),
                    slog.String("path", r.URL.Path),
                    slog.Int("status", rw.statusCode),
                    slog.Duration("duration", duration),
                }
                if span.SpanContext().IsValid() {
                    logAttrs = append(logAttrs,
                        slog.String("traceID", span.SpanContext().TraceID().String()),
                        slog.String("spanID", span.SpanContext().SpanID().String()),
                    )
                }
                logger.LogAttrs(ctx, slog.LevelInfo, "HTTP request handled", logAttrs...)
            })
        }
    }
    
    // (responseWriter struct and methods remain the same as in the provided code)
    type responseWriter struct {
        http.ResponseWriter
        statusCode int
    }
    func (rw *responseWriter) WriteHeader(statusCode int) {
        rw.statusCode = statusCode
        rw.ResponseWriter.WriteHeader(statusCode)
    }
    func (rw *responseWriter) Write(b []byte) (int, error) {
        return rw.ResponseWriter.Write(b)
    }

مرحله 3: استفاده در Handlerها (مثال در internal/server/handlers.go)

Handlerها Context را از درخواست دریافت می‌کنند و می‌توانند از توابع کمکی tracingpackage برای تعامل با Span فعال استفاده کنند.

package server
    
    import (
        "fmt"
        "log/slog"
        "net/http"
        "time"
    
        "sample-app/internal/service"
        "sample-app/tracingpackage" // Use our package
    
        "go.opentelemetry.io/otel/attribute"
        "go.opentelemetry.io/otel/codes"
    )
    
    type AppHandlers struct {
        logger      *slog.Logger
        tracer      tracingpackage.Tracer // Interface received via DI
        workService *service.WorkService
    }
    
    func NewAppHandlers(logger *slog.Logger, tracer tracingpackage.Tracer, workService *service.WorkService) *AppHandlers {
        return &AppHandlers{logger: logger, tracer: tracer, workService: workService}
    }
    
    func (h *AppHandlers) HandleHello(w http.ResponseWriter, r *http.Request) {
        // ctx already contains the server span from middleware
        ctx := r.Context()
    
        // Use helper functions to interact with the span in context
        tracingpackage.AddSpanAttributes(ctx, attribute.String("handler.name", "HandleHello"))
        tracingpackage.AddSpanEvent(ctx, "Processing /hello request")
        h.logger.InfoContext(ctx, "Handling /hello")
    
        time.Sleep(50 * time.Millisecond)
    
        tracingpackage.SetSpanStatus(ctx, codes.Ok, "Hello successful") // Explicitly set status if needed
    
        fmt.Fprintln(w, "Hello!")
    }
    
    func (h *AppHandlers) HandleWork(w http.ResponseWriter, r *http.Request) {
        ctx := r.Context()
        tracingpackage.AddSpanAttributes(ctx, attribute.String("handler.name", "HandleWork"))
        h.logger.InfoContext(ctx, "Handling /work, calling WorkService")
    
        // Pass the context down to the service layer
        err := h.workService.DoWork(ctx, 300*time.Millisecond)
        if err != nil {
            h.logger.ErrorContext(ctx, "WorkService failed", "error", err)
            // Record error using the helper function
            tracingpackage.RecordSpanError(ctx, err)
            // Status is automatically set to Error by RecordSpanError, but you could set it explicitly too
            // tracingpackage.SetSpanStatus(ctx, codes.Error, "WorkService error")
            http.Error(w, "Work failed", http.StatusInternalServerError)
            return
        }
    
        tracingpackage.AddSpanEvent(ctx, "WorkService call successful")
        tracingpackage.SetSpanStatus(ctx, codes.Ok, "Work successful")
    
        fmt.Fprintln(w, "Work done!")
    }

مرحله 4: استفاده در لایه سرویس (مثال در internal/service/work_service.go)

لایه سرویس Context را دریافت می‌کند و از Tracer تزریق شده برای ایجاد Spanهای فرزند استفاده می‌کند.

package service
    
    import (
        "context"
        "fmt"
        "log/slog"
        "time"
    
        "sample-app/tracingpackage" // Use our package
    
        "go.opentelemetry.io/otel/attribute"
        // "go.opentelemetry.io/otel/codes" // Not strictly needed if End(err) is used
    )
    
    type WorkService struct {
        logger *slog.Logger
        tracer tracingpackage.Tracer // Interface received via DI
    }
    
    func NewWorkService(logger *slog.Logger, tracer tracingpackage.Tracer) *WorkService {
        return &WorkService{logger: logger, tracer: tracer}
    }
    
    func (s *WorkService) DoWork(ctx context.Context, duration time.Duration) error {
        // Start a CHILD span using the injected tracer.
        // The parent span context is automatically picked up from `ctx`.
        ctx, span := s.tracer.Start(ctx, "service.WorkService.DoWork") // Descriptive span name
        defer span.End(nil) // IMPORTANT: Defer End immediately. Status/error updated below.
    
        s.logger.InfoContext(ctx, "Performing work in service")
    
        // Add service-specific attributes
        span.SetAttributes(attribute.Int64("work.duration.ms", duration.Milliseconds()))
        span.AddEvent("Starting simulated task")
    
        time.Sleep(duration) // Simulate work
    
        // Simulate potential error
        if duration > 400*time.Millisecond {
            err := fmt.Errorf("simulated task took too long: %v", duration)
            s.logger.ErrorContext(ctx, "Work simulation failed", "error", err)
            // CRITICAL: Call End again with the error. This records the error AND sets status to Error.
            span.End(err)
            return err
        }
    
        span.AddEvent("Simulated task finished")
        // No need to set Status OK explicitly if span.End(nil) is deferred and no error occurs.
    
        s.logger.InfoContext(ctx, "Work finished successfully in service")
        return nil
    }

نکات کلیدی بهترین شیوه‌ها:

  • تزریق وابستگی: همیشه tracingpackage.Tracer و otel.propagation.TextMapPropagator را به جای استفاده از globals، به کامپوننت‌ها تزریق کنید.
  • مدیریت Context: context.Context را همیشه به عنوان پارامتر اول به توابع و متدهایی که ممکن است در یک trace شرکت کنند، پاس دهید. از ctx برگشتی tracer.Start استفاده کنید.
  • استفاده از defer span.End(err): بلافاصله پس از tracer.Start، defer span.End(nil) (یا defer span.End(errVar) اگر متغیر خطا دارید) را فراخوانی کنید تا اطمینان حاصل شود Span همیشه بسته می‌شود. اگر خطایی رخ داد، span.End(actualError) را دوباره فراخوانی کنید تا خطا و وضعیت به درستی ثبت شوند.
  • نامگذاری معنادار Span: از نام‌های توصیفی برای Spanها استفاده کنید (مثلاً HTTP GET /route, package.Struct.Method, DB Query: GetUser).
  • Semantic Conventions: تا حد امکان از کلیدهای Attribute استاندارد semconv استفاده کنید.
  • ثبت خطاهای مرتبط: از span.RecordError(err) (یا تابع کمکی tracingpackage.RecordSpanError(ctx, err)) برای ثبت خطاهای Go در Span مربوطه استفاده کنید.
  • استفاده از توابع کمکی Context: توابع AddSpanAttributes, AddSpanEvent, RecordSpanError در tracingpackage کار با Span فعال در Context را ساده می‌کنند.
  • Graceful Shutdown: حتماً تابع ShutdownFunc برگردانده شده توسط NewTracerProvider را در زمان خاموش شدن برنامه فراخوانی کنید تا Spanهای بافر شده ارسال شوند.

7. اینترفیس‌های کلیدی (Important Interfaces)

tracingpackage دو اینترفیس اصلی برای تعامل با سیستم tracing ارائه می‌دهد:

  1. Tracer (در tracer.go)

    • هدف: انتزاعی برای ایجاد Spanهای جدید. کد شما به جای وابستگی مستقیم به oteltrace.Tracer، به این اینترفیس وابسته می‌شود.
    • متد اصلی:
      • Start(ctx context.Context, spanName string, opts ...SpanStartOption) (context.Context, Span):
        • یک Span جدید را شروع می‌کند.
        • spanName نام عملیات را مشخص می‌کند.
        • opts گزینه‌های اضافی OTel مانند oteltrace.WithSpanKind, oteltrace.WithAttributes را می‌پذیرد.
        • Context جدیدی را برمی‌گرداند که حاوی Span فعال است (باید از این ctx در ادامه استفاده شود).
        • نمونه‌ای از اینترفیس Span (wrapper ما) را برمی‌گرداند.
    • نحوه دریافت: با استفاده از tracingpackage.NewTracer(provider, instrumentationName).

  2. Span (در span.go)

    • هدف: انتزاعی برای کار با یک Span فعال. کد شما به جای وابستگی مستقیم به oteltrace.Span، با این اینترفیس کار می‌کند.
    • متدهای اصلی:
      • End(err error): Span را کامل می‌کند. زمان پایان را ثبت می‌کند و اگر err غیر nil باشد، خطا را ثبت و وضعیت را Error تنظیم می‌کند. فراخوانی این متد برای هر Span ضروری است.
      • RecordError(err error, options ...oteltrace.EventOption): یک خطای Go را به عنوان یک Event در Span ثبت می‌کند و وضعیت Span را به Error تغییر می‌دهد.
      • SetAttributes(kv ...attribute.KeyValue): یک یا چند Attribute (متادیتا) به Span اضافه می‌کند.
      • AddEvent(name string, options ...oteltrace.EventOption): یک رویداد زمانی (timestamped event) به Span اضافه می‌کند.
      • SetStatus(code codes.Code, description string): وضعیت Span (OK, Error, Unset) را به صراحت تنظیم می‌کند.
      • IsRecording() bool: بررسی می‌کند که آیا Span در حال ضبط اطلاعات است (یعنی sampled شده و هنوز End نشده).
      • SpanContext() oteltrace.SpanContext: Span Context منحصر به فرد Span را برمی‌گرداند.
      • TracerProvider() oteltrace.TracerProvider: TracerProvider مرتبط با Span را برمی‌گرداند.
    • نحوه دریافت: به عنوان مقدار بازگشتی از Tracer.Start() یا با استفاده از تابع کمکی tracingpackage.GetSpan(ctx).

توابع کمکی Context (در tracer.go):

این توابع مستقیماً با اینترفیس‌ها کار نمی‌کنند، اما روشی بسیار راحت برای تعامل با Span فعال در Context فعلی ارائه می‌دهند:

  • GetSpan(ctx context.Context) (Span, bool): Span فعال در ctx را (اگر معتبر و در حال ضبط باشد) به صورت اینترفیس Span برمی‌گرداند.
  • AddSpanAttributes(ctx context.Context, attrs ...attribute.KeyValue)
  • AddSpanEvent(ctx context.Context, name string, options ...oteltrace.EventOption)
  • RecordSpanError(ctx context.Context, err error, options ...oteltrace.EventOption)
  • SetSpanStatus(ctx context.Context, code codes.Code, description string)

استفاده از این توابع کمکی اغلب کد را خواناتر می‌کند، زیرا نیازی به نگهداری و پاس دادن مستقیم آبجکت Span نیست و فقط Context پاس داده می‌شود.

8. انتشار Context (Propagation Deep Dive)

چرا Propagation مهم است؟

در یک سیستم توزیع‌شده (مانند میکروسرویس‌ها)، یک درخواست کاربر ممکن است از چندین سرویس عبور کند. برای اینکه بتوانیم کل مسیر این درخواست را به عنوان یک Trace واحد مشاهده کنیم، باید راهی برای پیوند دادن Spanهای ایجاد شده در سرویس‌های مختلف وجود داشته باشد. این کار با انتشار (Propagate) اطلاعات شناسایی کلیدی (Trace ID, Span ID والد) از یک سرویس به سرویس بعدی انجام می‌شود.

نقش زیر-پکیج propagation/:

این زیر-پکیج مسئولیت مدیریت این فرآیند انتشار را بر عهده دارد:

  1. استانداردسازی فرمت‌ها (propagator.go):

    • سرویس‌های مختلف ممکن است از فرمت‌های انتشار متفاوتی استفاده کنند (یا نیاز به پشتیبانی از چندین فرمت برای سازگاری داشته باشند). استانداردهای رایج عبارتند از W3C Trace Context (توصیه شده) و B3.
    • تابع NewPropagator(formatsString) یک otel.propagation.TextMapPropagator ایجاد می‌کند که می‌تواند با فرمت‌های مشخص شده در پیکربندی (propagation.formats) کار کند.
    • معمولاً یک CompositePropagator ایجاد می‌شود که می‌تواند چندین فرمت را همزمان پشتیبانی کند. این به سیستم اجازه می‌دهد تا با سرویس‌هایی که از فرمت‌های مختلف استفاده می‌کنند، تعامل داشته باشد.
    • ترتیب در Composite: ترتیب فرمت‌ها در پیکربندی هنگام استخراج (Extract) مهم است. NewPropagator معمولاً TraceContext را در اولویت قرار می‌دهد. هنگام تزریق (Inject)، تمام فرمت‌های پشتیبانی شده تزریق می‌شوند.

  2. تعریف حامل‌ها (carriers.go):

    • اطلاعات Context چگونه حمل می‌شوند؟ این اطلاعات باید در جایی در درخواست خروجی (یا پیام) قرار گیرند. به این مکان “حامل” (Carrier) می‌گویند.
    • OpenTelemetry از اینترفیس propagation.TextMapCarrier برای انتزاع حامل‌های مبتنی بر متن (کلید-مقدار) استفاده می‌کند.
    • carriers.go پیاده‌سازی‌های مشخصی از این اینترفیس را برای حامل‌های رایج ارائه می‌دهد:
      • HTTPHeaderCarrier: برای خواندن/نوشتن Context در http.Header.
      • GrpcMetadataCarrier: برای خواندن/نوشتن Context در metadata.MD (مورد استفاده در gRPC).
    • این Carrierها به توابع Inject و Extract داده می‌شوند.

  3. ساده‌سازی تزریق و استخراج (propagator.go):

    • توابع کمکی Inject(ctx, propagator, carrier) و Extract(ctx, propagator, carrier) استفاده از Propagator را ساده می‌کنند.
    • Inject: Span Context فعال در ctx را می‌خواند و آن را با استفاده از propagator در carrier می‌نویسد (مثلاً هدرهای HTTP را تنظیم می‌کند). این تابع قبل از ارسال یک درخواست خروجی (HTTP, gRPC, …) فراخوانی می‌شود.
    • Extract: اطلاعات Context را از carrier (مثلاً هدرهای HTTP دریافتی) با استفاده از propagator می‌خواند و یک Context جدید حاوی Span Context استخراج شده برمی‌گرداند. این تابع پس از دریافت یک درخواست ورودی و قبل از شروع Span سرور فراخوانی می‌شود تا Span جدید به درستی به Trace والد پیوند بخورد.

مثال کاربردی:

  • سرویس A (کلاینت HTTP):
    1. tracer.Start() یک Span کلاینت ایجاد می‌کند (ctx جدید حاوی این Span است).
    2. یک HTTPHeaderCarrier از http.Request.Header ایجاد می‌شود.
    3. propagation.Inject(newCtx, propagator, carrier) فراخوانی می‌شود تا هدرهای traceparent, tracestate, b3 و … تنظیم شوند.
    4. درخواست HTTP به سرویس B ارسال می‌شود.
  • سرویس B (سرور HTTP):
    1. یک HTTPHeaderCarrier از هدرهای درخواست ورودی ایجاد می‌شود.
    2. requestCtx := propagation.Extract(r.Context(), propagator, carrier) فراخوانی می‌شود. propagator هدرها را می‌خواند و Span Context والد را پیدا می‌کند. requestCtx حالا حاوی Trace ID و Parent Span ID از سرویس A است.
    3. tracer.Start(requestCtx, ...) یک Span سرور ایجاد می‌کند که به طور خودکار فرزند Span کلاینت سرویس A می‌شود (چون requestCtx حاوی اطلاعات والد بود).

جداسازی منطق propagation در یک زیر-پکیج، کد را تمیز نگه می‌دارد و امکان افزودن پشتیبانی از Carrierها یا فرمت‌های جدید را در آینده آسان‌تر می‌کند.

9. نمونه‌برداری (Sampling Deep Dive)

چرا Sampling مهم است؟

در سیستم‌هایی با حجم ترافیک بالا، جمع‌آوری و ارسال داده‌های trace برای هر درخواست می‌تواند بار زیادی بر روی شبکه و سیستم‌های ذخیره‌سازی Observability تحمیل کند و همچنین هزینه قابل توجهی داشته باشد. علاوه بر این، پردازش این حجم عظیم داده نیز چالش‌برانگیز است.

نمونه‌برداری (Sampling) راهکاری برای این مشکل است. به جای ثبت تمام traceها، تنها درصدی از آن‌ها انتخاب و ثبت می‌شوند. هدف این است که یک نمای آماری معتبر از عملکرد سیستم به دست آوریم بدون اینکه هزینه و سربار ثبت ۱۰۰٪ traceها را متحمل شویم.

تصمیم نمونه‌برداری (Sampling Decision):

  • این تصمیم معمولاً در ابتدای trace (روی Root Span) گرفته می‌شود.
  • نتیجه تصمیم (اینکه trace باید sample شود یا نه) به عنوان بخشی از Span Context (در Trace Flags) در سراسر trace منتشر (propagate) می‌شود.
  • تمام Spanهای متعلق به یک trace باید از یک تصمیم نمونه‌برداری یکسان پیروی کنند؛ یا همه ثبت می‌شوند یا هیچ‌کدام (در مدل Head-based Sampling).

نقش زیر-پکیج sampling/:

این زیر-پکیج مسئولیت ایجاد یک نمونه Sampler از OpenTelemetry SDK بر اساس پیکربندی ارائه شده را دارد.

  • sampler.go:
    • تابع NewSampler(samplerType string, ratio float64, logger *slog.Logger):
      • ورودی‌های آن نوع سمپلر (sampler.type) و نرخ نمونه‌برداری (sampler.ratio) از Config هستند.
      • بر اساس samplerType، یکی از Samplerهای استاندارد OTel را برمی‌گرداند:
        • "always_on": sdktrace.AlwaysSample() - تمام traceها را نمونه‌برداری می‌کند. مناسب برای محیط‌های توسعه یا برای دیباگ کردن مشکلات خاص.
        • "always_off": sdktrace.NeverSample() - هیچ traceی را نمونه‌برداری نمی‌کند. (عملاً tracing را غیرفعال می‌کند).
        • "trace_id_ratio": sdktrace.TraceIDRatioBased(ratio) - به صورت تصادفی و بر اساس Trace ID، درصدی (ratio) از traceها را نمونه‌برداری می‌کند. این رایج‌ترین سمپلر برای محیط‌های پروداکشن است تا حجم داده‌ها کنترل شود. ratio باید بین 0.0 (هیچ‌کدام) و 1.0 (همه) باشد.

نحوه استفاده:

Sampler ایجاد شده توسط NewSampler در تابع NewTracerProvider (در provider.go) استفاده می‌شود و هنگام ساخت sdktrace.TracerProvider به آن پاس داده می‌شود:

// در provider.go
    func NewTracerProvider(cfg Config, logger *slog.Logger) (*sdktrace.TracerProvider, ShutdownFunc, error) {
        // ...
        // 3. Create Sampler
        smplr, err := sampling.NewSampler(cfg.Sampler.Type, cfg.Sampler.Ratio, logger)
        if err != nil {
            // ... handle error ...
            return nil, nil, fmt.Errorf("%w: failed to create sampler: %w", ErrProviderInitialization, err)
        }
        // ...
        // 4. Create Tracer Provider
        tpOpts := []sdktrace.TracerProviderOption{
            sdktrace.WithSampler(smplr), // <--- Sampler is configured here
            sdktrace.WithResource(res),
            // ...
        }
        tp := sdktrace.NewTracerProvider(tpOpts...)
        // ...
        return tp, actualShutdownFunc, nil
    }

انواع دیگر Sampling (که در این پکیج مستقیماً پیاده‌سازی نشده‌اند اما OTel پشتیبانی می‌کند):

  • ParentBased Sampler: این سمپلر رفتار خود را بر اساس والد Span تنظیم می‌کند. مثلاً اگر والد sampled شده باشد، فرزند هم sampled می‌شود. اگر والد sampled نشده باشد، فرزند هم نمی‌شود. اگر والد راه دور (remote) باشد یا Span ریشه باشد، از یک سمپلر داخلی دیگر (مثلاً TraceIDRatioBased) برای تصمیم‌گیری استفاده می‌کند. این سمپلر پیش‌فرض OTel SDK است و انعطاف‌پذیری خوبی دارد. tracingpackage با تنظیم صریح یکی از سمپلرهای پایه (AlwaysOn, AlwaysOff, TraceIDRatioBased)، به طور ضمنی ParentBased را bypass می‌کند، اما می‌توانست طوری طراحی شود که ParentBased را با یکی از این‌ها به عنوان ریشه پیکربندی کند.
  • Tail-based Sampling: در این روش، تصمیم نمونه‌برداری در انتهای trace و پس از جمع‌آوری تمام Spanهای آن گرفته می‌شود (معمولاً در OTel Collector). این امکان را می‌دهد که traceها بر اساس ویژگی‌های کل trace (مثلاً وجود خطا، داشتن duration بالا، یا داشتن attribute خاص) انتخاب شوند. این روش تضمین می‌کند که traceهای مهم از دست نمی‌روند، اما پیچیده‌تر است و نیاز به منابع بیشتری در Collector دارد. tracingpackage فقط Head-based Sampling (تصمیم در ابتدا) را پیاده‌سازی می‌کند.

جداسازی منطق sampling به تمیزی کد کمک می‌کند و تمرکز هر بخش را مشخص می‌نماید. انتخاب Sampler و Ratio مناسب، یک توازن مهم بین میزان دید (visibility) مورد نیاز و هزینه/سربار tracing است.

10. سناریوی استفاده در میکروسرویس (Microservice Usage Scenario)

بیایید یک سناریوی واقعی را دنبال کنیم که یک درخواست کاربر از طریق چندین میکروسرویس عبور می‌کند و ببینیم tracingpackage در هر مرحله چگونه عمل می‌کند.

مفروضات:

  • سه میکروسرویس داریم: GatewayService (نقطه ورود، Go)، OrderService (Go)، PaymentService (Go).
  • همه سرویس‌ها از tracingpackage برای راه‌اندازی OTel استفاده می‌کنند.
  • GatewayService با OrderService از طریق HTTP ارتباط برقرار می‌کند.
  • OrderService با PaymentService از طریق gRPC ارتباط برقرار می‌کند.
  • یک Backend برای مشاهده Traces (مانند Jaeger یا یک OTel Collector که به Jaeger می‌فرستد) وجود دارد.
  • پیکربندی tracingpackage در همه سرویس‌ها شامل موارد زیر است:
    • exporter.type: "otlp_grpc" (ارسال به یک کالکتور مرکزی)
    • sampler.type: "trace_id_ratio", sampler.ratio: 0.1 (نمونه‌برداری 10%)
    • propagation.formats: "tracecontext,b3" (پشتیبانی از W3C و B3)

مراحل درخواست:

  1. ورود درخواست به GatewayService:

    • یک درخواست POST /orders از کاربر به GatewayService می‌رسد.
    • TracingMiddleware (در GatewayService) فعال می‌شود:
      • propagation.Extract(): با استفاده از propagator (که از NewPropagator گرفته شده) و HTTPHeaderCarrier، هدرهای ورودی (traceparent, b3, …) را بررسی می‌کند. چون این اولین سرویس است، هیچ Context معتبری پیدا نمی‌شود. requestCtx اولیه برگردانده می‌شود.
      • tracer.Start(requestCtx, "POST /orders", oteltrace.WithSpanKind(oteltrace.SpanKindServer)):
        • چون Context ورودی والد نداشت، Sampler (که TraceIDRatioBased(0.1) است) فراخوانی می‌شود. فرض کنیم این Trace تصمیم به نمونه‌برداری می‌گیرد (Sampled=true).
        • یک Trace ID جدید و یک Span ID جدید (Span A) ایجاد می‌شود.
        • یک Span سرور جدید با نام POST /orders و Span Context (TraceID, SpanID A, Sampled=true) ایجاد می‌شود.
        • Context جدیدی (ctxA) حاوی این Span فعال برگردانده می‌شود.
      • defer span.End(nil): پایان Span A به تعویق می‌افتد.
      • r = r.WithContext(ctxA): درخواست HTTP با Context به‌روز شده حاوی Span A جایگزین می‌شود.
      • next.ServeHTTP(): کنترل به Handler مربوط به /orders داده می‌شود.

  2. پردازش در GatewayService Handler:

    • Handler ctx := r.Context() را فراخوانی می‌کند و ctxA را دریافت می‌کند.
    • ممکن است از tracingpackage.AddSpanAttributes(ctxA, ...) برای افزودن اطلاعات به Span A استفاده کند.
    • Handler تصمیم می‌گیرد با OrderService از طریق HTTP تماس بگیرد. فرض کنیم از یک کلاینت HTTP استاندارد net/http استفاده می‌کند که با otelhttp (بخشی از otel contrib) instrument شده است (یا از یک Middleware کلاینت مشابه استفاده می‌کند).

  3. فراخوانی OrderService از GatewayService (HTTP Client):

    • Instrumentation کلاینت HTTP (مثلاً otelhttp.Transport) فعال می‌شود:
      • tracer.Start(ctxA, "HTTP POST /orders", oteltrace.WithSpanKind(oteltrace.SpanKindClient)):
        • ctxA حاوی Span A است، بنابراین این Span جدید (Span B) به طور خودکار فرزند Span A می‌شود (ParentSpanID = SpanID A).
        • Trace ID و فلگ Sampled=true از ctxA به ارث می‌رسند.
        • Context جدید (ctxB) حاوی Span B برگردانده می‌شود.
      • propagation.Inject(ctxB, propagator, httpHeaderCarrier):
        • Span Context مربوط به Span B (TraceID, SpanID B, Sampled=true) خوانده می‌شود.
        • propagator (که از NewPropagator گرفته شده و tracecontext,b3 را پشتیبانی می‌کند) هدرهای traceparent و b3 را در http.Request.Header که به OrderService ارسال می‌شود، تنظیم می‌کند.
      • درخواست HTTP به OrderService ارسال می‌شود.
      • پس از دریافت پاسخ از OrderService:
        • Span B با اطلاعات پاسخ (status code) به‌روز می‌شود.
        • spanB.End() فراخوانی می‌شود. Span B تکمیل شده و آماده ارسال توسط BatchSpanProcessor در GatewayService است.
    • کنترل به Handler GatewayService باز می‌گردد.

  4. ورود درخواست به OrderService:

    • درخواست HTTP از GatewayService می‌رسد.
    • TracingMiddleware (در OrderService) فعال می‌شود:
      • propagation.Extract(): هدرهای ورودی (traceparent, b3) را با استفاده از propagator (که در OrderService پیکربندی شده) می‌خواند. Span Context معتبری با TraceID اصلی و ParentSpanID=SpanID B پیدا می‌شود. requestCtx حاوی این Context استخراج شده برگردانده می‌شود.
      • tracer.Start(requestCtx, "HTTP POST /orders", oteltrace.WithSpanKind(oteltrace.SpanKindServer)):
        • چون requestCtx حاوی Context والد (Sampled=true) است، Sampler در OrderService دیگر تصمیم نمی‌گیرد؛ تصمیم والد (Sampled=true) رعایت می‌شود.
        • یک Span ID جدید (Span C) ایجاد می‌شود.
        • یک Span سرور جدید با نام HTTP POST /orders ایجاد می‌شود که فرزند Span B است (TraceID, SpanID C, ParentSpanID B, Sampled=true).
        • Context جدید (ctxC) حاوی Span C برگردانده می‌شود.
      • defer span.End(nil): پایان Span C به تعویق می‌افتد.
      • r = r.WithContext(ctxC): درخواست با Context به‌روز شده جایگزین می‌شود.
      • next.ServeHTTP(): کنترل به Handler مربوطه داده می‌شود.

  5. پردازش در OrderService Handler و فراخوانی PaymentService (gRPC Client):

    • Handler ctxC را دریافت می‌کند.
    • منطق ایجاد سفارش را اجرا می‌کند.
    • تصمیم می‌گیرد با PaymentService از طریق gRPC تماس بگیرد. فرض کنیم از یک کلاینت gRPC استفاده می‌کند که با otelgrpc (از otel contrib) instrument شده است.
    • Instrumentation کلاینت gRPC (مثلاً otelgrpc.UnaryClientInterceptor) فعال می‌شود:
      • tracer.Start(ctxC, "PaymentService/ProcessPayment", oteltrace.WithSpanKind(oteltrace.SpanKindClient)):
        • یک Span کلاینت جدید (Span D) به عنوان فرزند Span C ایجاد می‌شود (TraceID, SpanID D, ParentSpanID C, Sampled=true).
        • Context جدید (ctxD) حاوی Span D برگردانده می‌شود.
      • propagation.Inject(ctxD, propagator, grpcMetadataCarrier):
        • Span Context مربوط به Span D خوانده می‌شود.
        • propagator هدرهای traceparent و b3 (با کلیدهای lowercase) را در metadata.MD خروجی gRPC تزریق می‌کند.
      • فراخوانی gRPC به PaymentService ارسال می‌شود.
      • پس از دریافت پاسخ gRPC:
        • Span D با وضعیت پاسخ به‌روز می‌شود.
        • spanD.End() فراخوانی می‌شود. Span D آماده ارسال توسط BatchSpanProcessor در OrderService است.
    • کنترل به Handler OrderService باز می‌گردد.

  6. ورود درخواست به PaymentService (gRPC Server):

    • فراخوانی gRPC از OrderService می‌رسد.
    • Instrumentation سرور gRPC (مثلاً otelgrpc.UnaryServerInterceptor) فعال می‌شود:
      • propagation.Extract(): با استفاده از propagator (در PaymentService) و GrpcMetadataCarrier، متادیتای ورودی را می‌خواند و Span Context معتبر (TraceID, ParentSpanID D, Sampled=true) را پیدا می‌کند. requestCtx حاوی این Context استخراج شده است.
      • tracer.Start(requestCtx, "PaymentService/ProcessPayment", oteltrace.WithSpanKind(oteltrace.SpanKindServer)):
        • یک Span سرور جدید (Span E) به عنوان فرزند Span D ایجاد می‌شود (TraceID, SpanID E, ParentSpanID D, Sampled=true).
        • Context جدید (ctxE) حاوی Span E برگردانده می‌شود.
      • Handler متد gRPC با ctxE فراخوانی می‌شود.

  7. پردازش در PaymentService Handler:

    • Handler ctxE را دریافت می‌کند.
    • منطق پردازش پرداخت را انجام می‌دهد (ممکن است Spanهای داخلی بیشتری ایجاد کند).
    • Attributes و Events مرتبط را به Span E اضافه می‌کند.
    • پس از اتمام کار، Handler پاسخ gRPC را برمی‌گرداند.
    • Instrumentation سرور gRPC (ادامه):
      • وضعیت پاسخ gRPC روی Span E ثبت می‌شود.
      • spanE.End() فراخوانی می‌شود. Span E آماده ارسال توسط BatchSpanProcessor در PaymentService است.

  8. بازگشت پاسخ‌ها:

    • پاسخ gRPC به OrderService برمی‌گردد. Handler آن تکمیل می‌شود.
    • TracingMiddleware (در OrderService - ادامه): وضعیت نهایی پاسخ HTTP روی Span C ثبت می‌شود. spanC.End() فراخوانی می‌شود. Span C آماده ارسال است.
    • پاسخ HTTP به GatewayService برمی‌گردد. Handler آن تکمیل می‌شود.
    • TracingMiddleware (در GatewayService - ادامه): وضعیت نهایی پاسخ HTTP به کاربر روی Span A ثبت می‌شود. spanA.End() فراخوانی می‌شود. Span A آماده ارسال است.

نتیجه نهایی:

تمام Spanها (A, B, C, D, E) که همگی Sampled=true بودند، از طریق Exporterهای OTLP در هر سرویس به OTel Collector (و سپس به Jaeger) ارسال می‌شوند. چون همگی Trace ID یکسانی دارند و روابط والد-فرزندی (ParentSpanID) به درستی از طریق propagation حفظ شده است، Jaeger می‌تواند کل این Trace توزیع‌شده را به صورت یک نمودار آبشاری (waterfall chart) نمایش دهد که دقیقاً نشان می‌دهد درخواست چقدر زمان در هر سرویس و در هر مرحله (HTTP call, gRPC call, processing) صرف کرده است.

این سناریو قدرت tracingpackage را در ساده‌سازی و استانداردسازی پیاده‌سازی tracing در یک محیط پیچیده نشان می‌دهد.

11. تست کردن (Testing)

یکی از مزایای کلیدی استفاده از tracingpackage و اینترفیس‌های Tracer و Span، بهبود قابلیت تست کد شماست. به جای وابستگی مستقیم به انواع کانکریت OTel SDK، کد شما به اینترفیس‌ها وابسته است که به راحتی می‌توان آن‌ها را در تست‌های واحد (Unit Tests) جعل (mock) کرد.

روش‌های تست:

  1. Mocking Interfaces:

    • شما می‌توانید پیاده‌سازی‌های mock (جعلی) از اینترفیس‌های tracingpackage.Tracer و tracingpackage.Span ایجاد کنید. کتابخانه‌های mocking مانند testify/mock یا gomock می‌توانند در این زمینه کمک کنند.
    • سناریو: فرض کنید می‌خواهید متد DoWork در WorkService را تست کنید. WorkService یک tracingpackage.Tracer را به عنوان وابستگی دریافت می‌کند.
    • در تست:
      • یک mockTracer ایجاد کنید که اینترفیس Tracer را پیاده‌سازی کند.
      • یک mockSpan ایجاد کنید که اینترفیس Span را پیاده‌سازی کند.
      • mockTracer.On("Start", mock.Anything, "service.WorkService.DoWork").Return(context.Background(), mockSpan) را تنظیم کنید تا هنگام فراخوانی Start، mockSpan شما برگردانده شود.
      • mockSpan.On("End", mock.AnythingOfType("*fmt.wrapError")) (یا nil بسته به سناریو) را تنظیم کنید تا فراخوانی End را انتظار داشته باشید.
      • همچنین می‌توانید فراخوانی‌های SetAttributes, AddEvent, RecordError را روی mockSpan انتظار داشته باشید و تأیید کنید که با مقادیر صحیح فراخوانی می‌شوند.
      • WorkService را با mockTracer نمونه‌سازی کنید و متد DoWork را فراخوانی نمایید.
      • در نهایت، با استفاده از توابع AssertExpectations(t) کتابخانه mock، تأیید کنید که تمام تعاملات مورد انتظار با Tracer و Span رخ داده‌اند.
    // مثال بسیار ساده با testify/mock
    package service_test
    
    import (
        "context"
        "errors"
        "testing"
        "time"

        "github.com/stretchr/testify/mock"

        "sample-app/internal/service"
        // "sample-app/tracingpackage" // Import the actual package if needed for types
    )
    
    // --- Mock Tracer ---
    type MockTracer struct {
        mock.Mock
        // Embed the interface to satisfy it implicitly (optional but good practice)
        // tracingpackage.Tracer
    }
    
    func (m *MockTracer) Start(ctx context.Context, spanName string, opts ...oteltrace.SpanStartOption) (context.Context, tracingpackage.Span) { // Use oteltrace.SpanStartOption

        // Return concrete types if possible, otherwise interfaces
        return args.Get(0).(context.Context), args.Get(1).(tracingpackage.Span)
    }
    
    
    // --- Mock Span ---
    type MockSpan struct {
        mock.Mock
        // tracingpackage.Span
    }
    
    func (m *MockSpan) End(err error) {
        m.Called(err)
    }
    func (m *MockSpan) RecordError(err error, options ...oteltrace.EventOption) {
        m.Called(err, options) // Pass options variadically
    }
    func (m *MockSpan) SetAttributes(kv ...attribute.KeyValue) {
        m.Called(kv) // Pass kv variadically
    }
    func (m *MockSpan) AddEvent(name string, options ...oteltrace.EventOption) {
        m.Called(name, options) // Pass options variadically
    }
    func (m *MockSpan) IsRecording() bool {
        args := m.Called()
        return args.Bool(0)
    }
    func (m *MockSpan) SpanContext() oteltrace.SpanContext {
        args := m.Called()
        return args.Get(0).(oteltrace.SpanContext) // Assuming you return a valid SpanContext
    }
    func (m *MockSpan) TracerProvider() oteltrace.TracerProvider {
        args := m.Called()
        return args.Get(0).(oteltrace.TracerProvider) // Assuming you return a valid Provider
    }
     func (m *MockSpan) SetStatus(code codes.Code, description string) {
        m.Called(code, description)
    }

    func TestWorkService_DoWork_Success(t *testing.T) {
        mockTracer := new(MockTracer)
        mockSpan := new(MockSpan)
        mockCtx := context.Background() // Or a relevant context
    
        // Expect Start to be called and return the mock span
        mockTracer.On("Start", mockCtx, "service.WorkService.DoWork", mock.AnythingOfType("[]trace.SpanStartOption")).Return(mockCtx, mockSpan)
    
        // Expect span interactions
        mockSpan.On("SetAttributes", mock.AnythingOfType("[]attribute.KeyValue")).Return()
        mockSpan.On("AddEvent", "Starting simulated task", mock.AnythingOfType("[]trace.EventOption")).Return()
        mockSpan.On("AddEvent", "Simulated work finished successfully", mock.AnythingOfType("[]trace.EventOption")).Return()
        // Expect End(nil) because it's success case
        mockSpan.On("End", nil).Return()
        // Expect SetStatus(codes.Ok, "Work completed") might be called explicitly or implicitly
        // mockSpan.On("SetStatus", codes.Ok, "Work completed").Return()

        // Assuming logger is nil or mocked as well for simplicity here
        svc := service.NewWorkService(nil, mockTracer)
    
        // Call the method
        err := svc.DoWork(mockCtx, 100*time.Millisecond)
    
        // Assertions
        assert.NoError(t, err)
        mockTracer.AssertExpectations(t)
        mockSpan.AssertExpectations(t)
    }
    
     func TestWorkService_DoWork_Error(t *testing.T) {
        mockTracer := new(MockTracer)
        mockSpan := new(MockSpan)
        mockCtx := context.Background()
        simulatedError := errors.New("simulated task took too long: 600ms")
    
        // Expect Start
        mockTracer.On("Start", mockCtx, "service.WorkService.DoWork", mock.AnythingOfType("[]trace.SpanStartOption")).Return(mockCtx, mockSpan)
    
        // Expect span interactions for the error path
        mockSpan.On("SetAttributes", mock.AnythingOfType("[]attribute.KeyValue")).Return()
        mockSpan.On("AddEvent", "Starting simulated task", mock.AnythingOfType("[]trace.EventOption")).Return()
        // Expect RecordError is NOT called directly inside DoWork if using End(err)
        // Expect End(err) to be called with the specific error
        mockSpan.On("End", simulatedError).Return() // Expect End to be called with the error
    
        svc := service.NewWorkService(nil, mockTracer)
        err := svc.DoWork(mockCtx, 600*time.Millisecond)
    
        assert.Error(t, err)
        assert.Equal(t, simulatedError.Error(), err.Error()) // Check the error message if needed
        mockTracer.AssertExpectations(t)
        mockSpan.AssertExpectations(t) // Verifies End(simulatedError) was called
    }

  2. Integration Testing with Console/InMemory Exporter:

    • برای تست‌های یکپارچه‌سازی (Integration Tests) که می‌خواهید رفتار واقعی tracing را بررسی کنید اما نمی‌خواهید به یک Backend خارجی وابسته باشید:
      • می‌توانید tracingpackage را با exporter.type: "console" پیکربندی کنید. Spanها در خروجی چاپ می‌شوند و می‌توانید آن‌ها را بررسی کنید (اگرچه تجزیه خروجی کنسول ممکن است شکننده باشد).
      • روش بهتر: از InMemoryExporter خود OpenTelemetry SDK استفاده کنید. اگرچه tracingpackage مستقیماً آن را به عنوان یک نوع اکسپورتر پیکربندی‌شده ارائه نمی‌دهد، می‌توانید در کد تست خود یک TracerProvider با InMemoryExporter بسازید (با استفاده از otel sdk/trace/tracetest) و آن را به کامپوننت‌های خود تزریق کنید. سپس پس از اجرای تست، می‌توانید Spanهای جمع‌آوری شده در حافظه را بازرسی کرده و ویژگی‌ها، رویدادها و وضعیت آن‌ها را تأیید کنید.
    // مثال مفهومی برای استفاده از InMemoryExporter در تست
    package main_test
    
    import (
        "context"
        "net/http"
        "net/http/httptest"
        "testing"
    
        "github.com/stretchr/testify/assert"
        "go.opentelemetry.io/otel/sdk/trace"
        "go.opentelemetry.io/otel/sdk/trace/tracetest" // Import for testing utilities
    
        "sample-app/internal/server"
        "sample-app/internal/service"
        "sample-app/tracingpackage"
        tpropagation "sample-app/tracingpackage/propagation"
    )
    
    func TestIntegration_HandleWork_CreatesSpans(t *testing.T) {
        // 1. Create an InMemoryExporter
        exporter := tracetest.NewInMemoryExporter()
    
        // 2. Create a TracerProvider using the exporter (and simple config)
        //    We bypass tracingpackage.NewTracerProvider here for direct control in test
        tp := trace.NewTracerProvider(
            trace.WithBatcher(exporter),
            // Add Resource, Sampler if needed for the test
            trace.WithSampler(trace.AlwaysSample()), // Ensure spans are recorded
        )
        defer func() { _ = tp.Shutdown(context.Background()) }() // Shutdown provider
    
        // 3. Create Propagator and Tracer using the test provider
        propagator := tpropagation.NewPropagator("tracecontext") // Simple propagator
        testTracer := tracingpackage.NewTracer(tp, "test-service") // Use our interface
    
        // 4. Setup dependencies with the test tracer
        // Assuming logger is nil for simplicity
        workSvc := service.NewWorkService(nil, testTracer)
        appHandlers := server.NewAppHandlers(nil, testTracer, workSvc)
    
        // 5. Setup the HTTP server with middleware using the test tracer/propagator
        mux := http.NewServeMux()
        mux.HandleFunc("GET /work", appHandlers.HandleWork)
        tracingMW := server.TracingMiddleware(nil, testTracer, propagator)
        testServer := httptest.NewServer(tracingMW(mux))
        defer testServer.Close()
    
        // 6. Make a request to the test server
        req, _ := http.NewRequest("GET", testServer.URL+"/work", nil)
        client := testServer.Client()
        _, err := client.Do(req)
        assert.NoError(t, err)
    
        // 7. Force flush spans (important!)
        err = tp.ForceFlush(context.Background())
        assert.NoError(t, err)
    
        // 8. Get recorded spans from the InMemoryExporter
        recordedSpans := exporter.GetSpans()
    
        // 9. Assertions on the recorded spans
        assert.Len(t, recordedSpans, 2, "Expected 2 spans (server + service)")
    
        var serverSpan, serviceSpan trace.ReadOnlySpan
        for _, s := range recordedSpans {
            // Identify spans based on name or attributes
            if s.Name() == "GET /work" {
                serverSpan = s
            } else if s.Name() == "service.WorkService.DoWork" {
                serviceSpan = s
            }
        }
    
        assert.NotNil(t, serverSpan, "Server span not found")
        assert.NotNil(t, serviceSpan, "Service span not found")
    
        // Check parent-child relationship
        assert.Equal(t, serverSpan.SpanContext().TraceID(), serviceSpan.SpanContext().TraceID())
        assert.Equal(t, serverSpan.SpanContext().SpanID(), serviceSpan.Parent().SpanID())
